# 《帝王三国》APK `assets/data/*.dat` 格式与用途分析报告

- 分析对象：`/root/.hermes/cache/documents/doc_35366e2e3838_帝王三國繁體版.apk.1`（92,914,352 字节，标准 zip）
- 分析方式：`python3 zipfile` 直接读取内部文件（未解压整包），逐字节统计 + 反猜测验证
- 样本规模：`assets/data/` 下 **9475** 个 `.dat`，全部读入内存做全量统计（不是抽样）
- 中间产物：`/root/帝王三国/apk_analysis/dat_all.csv`（id, size, 类型字节, IHDR 次数, 首个 IHDR 偏移, 头 16 字节）

---

## 0. 一句话结论

`assets/data/<id>.dat` **不是**消息/协议字段定义，而是**游戏引擎（`engineBase.res.*`）的资源对象包**，以数字 **资源 id** 为文件名和首字段。
它里面装的是 **PNG 图片（去掉 8 字节 PNG 签名）、精灵帧表、地图/图层数据、资源引用记录**。
**无法**从这些文件推出任何协议消息（例如 op 4128 响应）的字段名/类型/顺序。

---

## 1. 通用容器头（全量 9475/9475 验证）

所有 `.dat` 的前 3 字节结构完全一致：

```
偏移  长度  含义                        验证
0x00   2    u16 BE 资源 id（== 文件名数字） 9475/9475 全部相等
0x02   1    u8 资源类型（type）           取值只有 {0x01,0x03,0x04,0x05,0x06,0x0d}
0x03   ...  按 type 而定的结构体
```

关键点：**「文件名 == 文件头前 2 字节」不是巧合，而是构造性事实**。
9475 个文件一个例外都没有。因此「0x1020 = 4128 ✓」这类"验证"**不能**证明这些 id 就是协议操作码——它对任何数字都成立。

type 分布（和 = 9475）：

| type | 个数 | 结构特征 |
|---|---|---|
| `0x01` | 6134 | 图片（PNG 数据，去掉 8 字节签名）+ 可选精灵帧表 |
| `0x06` | 3015 | 固定 6 字节：`[id][0x06][u16 父资源id][u8 帧序号]` |
| `0x03` | 187 | 26~2060 字节，内含若干 `28 01 <u16 图片id>` 记录 |
| `0x05` | 70 | 固定 7 字节：`[id][0x05][u16 目标id][u16 flags]` |
| `0x0d` | 60 | 图片（PNG 风格，但 chunk 头被压扁/改写，zlib 流头为 `78 5e`） |
| `0x04` | 9 | 大文件（678~222328 字节）：地图/图集（含 tile 数据 + 子资源位置表） |

## 2. type 0x01（图片）精确格式

```
[0x00:0x02] u16 BE  资源 id
[0x02]      u8      0x01
[0x03:0x05] u16 BE  宽 width      ← 与 PNG IHDR 的宽完全一致（6134/6134）
[0x05:0x07] u16 BE  高 height     ← 与 PNG IHDR 的高完全一致（6134/6134）
[0x07]      u8      N = 精灵帧数（"子图"记录条数）
[0x08]      u8      0（个别文件为 5/8/1，见 §2.2 不确定项）
[0x09:0x0d] u32 BE  当 N==0 时为 PNG 负载长度（= 文件大小-13）；否则为 0
[0x0d : 0x0d+8N]    N 条 8 字节记录
[0x0d+8N-4 : 0x0d+8N] u32 BE 负载长度（= 文件大小 - (13+8N)）   ← 6134/6134 成立
[0x0d+8N : EOF]     PNG 数据流：从 IHDR 的 chunk 长度字段开始，**没有 8 字节 PNG 签名**
                    且**没有 IEND chunk**（6134/6134 全都没有）：流 = IHDR + IDAT(可多段) 到文件末尾。
                    例：929.dat 去掉 13 字节头后补回签名，可完整解析出 IHDR(13) + IDAT(454)，正好到 EOF。
```

### 2.1 验证细节（可复算）

头部长度与 N 的对应关系（全量统计，无例外）：

```
N=0  → 头长 13   : 5613 个文件
N=1  → 头长 21   :  173 个文件
N=2  → 头长 29   :   32 个文件
N=3  → 头长 37   :   24 个
N=4  → 头长 45   :   30 个
N=5..25,32 → 头长 = 13+8N  （最大 N=32 → 头长 269，5 个文件）
```
即 **头长 ≡ 13 + 8N（严格成立），且头末 4 字节恒等于负载长度**。

hex 证据（0.dat，N=0，最小样本）：
```
00 00 | 01 | 00 80 | 00 40 | 00 | 00 | 00 00 1c a2 | 00 00 00 0d 49 48 44 52 ...
 id=0   t=1   W=128   H=64   N=0        len=7330        chunk_len=13 'IHDR'
文件大小 7343 = 13 + 7330 ✓
```

hex 证据（929.dat，16×14 图标；`assets/929.dat` 与 `assets/data/929.dat` **字节完全相同**）：
```
03 a1 | 01 | 00 10 | 00 0e | 00 | 00 | 00 00 01 eb | 00 00 00 0d 49 48 44 52 ...
 id=929  t=1   W=16    H=14   N=0        len=491         正是一个完整 PNG 去掉签名后的头部
```

hex 证据（1116.dat，N=1，73×36）：
```
04 5c 01 00 49 00 24 01 | 00 00 00 00 | 49 00 24 00 | 00 00 10 46 | 00 00 00 0d 49 48 44 52 ...
id=1116 t=1  W=73  H=36  N=1            (73,36)         len=4166      IHDR
文件大小 4187 = 21 + 4166 ✓
```

### 2.2 精灵帧表（8 字节记录）——部分解读，含不确定项

以 4099.dat（进入游戏界面资源，104473 字节，W=400 H=200，**N=32**）为例，256 字节记录区（小端 u16 读法）：

```
(50, 50,  50,   0)  (50, 50, 100,   0)  (50, 50, 150,   0)  (50, 50, 200,   0)
(50, 50, 250,   0)  (50,306,  44,   0)  (50,306,  94,   0)
(50, 50,   0,  50)  (50, 50,  50,  50)  (50, 50, 100,  50)  ...
(50, 50,   0, 150)  ...                                   (50,306,  94, 150)
尾部 8 字节: 32 00 32 00 | 00 01 97 0c   → (50,50) + u32 负载长度 104204
```

可以确认的：
- 每条记录 8 字节，共 N 条（4099 是 32 条，正好等于 **400/50 × 200/50 = 8×4 = 32** 个 50×50 格）。
- 记录里 `0x32`(50) 反复出现，且出现 (0,50,100,150) 这类整齐的 50 步进值 → 结构是**子图矩形/帧信息**（宽高 + 坐标）。
- 帧表末尾 4 字节是 u32 BE 负载长度（与头长公式互证）。

**不确定的部分**：部分记录（如 `32 00 32 01 2c 00 00 00`）不满足朴素的 `(w,h,x,y)` 元组约束（会出现 y=306 > 图高 200 的情形），说明字段打包方式不是简单的四个 u16，可能含变长/混合编码。**该 8 字节记录的确切字段顺序尚未完全确定**——报告中不做断言。
（dex 中确有 `engineBase/res/SpriteInfo$SpriteFrame;` 类，方法 `getSpriteFrameNum()/getSpriteFrame()/setSpriteFrame()`，与「N = 帧数」吻合，但未反编译确认字段名。）

## 3. type 0x06（3015 个）与 4128.dat 的确切解读

### 3.1 格式

```
[0x00:0x02] u16 BE  自身 id
[0x02]      u8      0x06
[0x03:0x05] u16 BE  父资源 id（引用另一张精灵图/资源）
[0x05]      u8      帧序号（全量统计：**3015/3015 个文件都 ≤ 31**，即 0..31）
```
共 6 字节，所以 3015 个文件大小全部恰好为 6（无例外）。

### 3.2 4128.dat 六个字节的逐字节解读

```
hex: 10 20 06 10 03 1c

10 20  → u16 BE = 4128          = 自身资源 id（与文件名一致）
06     → 资源类型 = 0x06（精灵帧引用）
10 03  → u16 BE = 4099          = 父资源 id（4099.dat = 400×200、32 帧的图片资源）
1c     → u8      = 28            = 帧序号（第 28 帧，0 起算）
```

即 **「4128 号资源 = 4099 号精灵图里的第 28 帧」**。这是一个**资源指针**，不携带任何消息字段信息。

### 3.3 支持该解读的硬证据

1. **4100..4131 全部指向同一个父 4099，序号恰好 0..31 各一次**：
   ```
   4100 → (4099, 0)   4108 → (4099, 8)    …    4128 → (4099, 28)   4131 → (4099, 31)
   hex: 4100=100406100300  4108=100c06100308  4128=10200610031c  4131=10230610031f
   ```
   而 4099.dat 的 `N=32`，图 400×200、格子 50×50 → 正好 32 格。**父子两边的数字严丝合缝**。
2. 引用合法性：3015 个 type-6 文件中，`[3:5]` 是**真实存在的资源 id** 的有 **3005/3015（99.7%）**。
   剩下 10 个引用的是本 APK 未打包的 id（如 397→374、587→549），符合「引用可指向未随包资源」的行为。
3. 排除了另一种读法（`[3]=0x10 标记` + `[4:6]=u16 资源id`，即 4128 → 796）：
   - 按该读法全量统计，`[4:6]` 是有效资源 id 的只有 **492/3015（16%）**，而 `[3:5]` 读法是 99.7%；
   - type-5 同类统计更极端：`[3:5]` 读法 **70/70 全有效**，`[4:6]` 读法只有 10/70。
   故 `[3:5]` 读法成立。

### 3.4 type 0x05（70 个）旁证同一个「引用」体系

```
[0x00:0x02] 自身 id | 0x05 | [0x03:0x05] u16 目标id | [0x05:0x07] u16 flags
```
- 目标 id 有效率 **70/70**；
- 目标类型**全部是 0x0d**（即"某个 0x0d 图片资源的别名/变体"）；
- flags 取值只有 {0x01FF, 0x02FF, 0x03FF, 0x0000} —— 典型的标志位（缩放/翻转/旋转之类）。

## 4. id 分布规律

- id 范围 **0 ~ 13143**，实际存在 **9475** 个，缺 **3669** 个；
- 不是"每段一个功能"的整齐分段，而是 **294 个连续区间**（最大连续段 588 个：12556~13143），**82 个孤立 id**；

## 5. 有没有可读字符串 / 是否有字段名

- 9475 个 `.dat` **全部没有 UTF-8 中文字符串**，没有字段名、没有 `name/type/len` 之类的自描述标签。
  （初次统计中"含 0xe0~0xe9 字节的 6347 个文件"是随机二进制数据的假阳性：逐个检查这些字节前后并不构成合法 UTF-8 序列。）
- 文本只存在于**同类目录**的其他文件里，例如：
  - `assets/script/sentence.txt`（315KB，`#1\tdi_联网军情获取\t軍情獲取…` 纯文本文案表）
  - `assets/script/*.sc`（226 个二进制配置表，UTF-8 名称 + u16 计数 + 行记录，如 `scriptItem.sc`、`scriptSkill.sc`、`scriptRoleProf.sc` → 道具/技能/职业数值表）
  这些是**游戏数值配置**，同样没有协议字段结构。

## 6. 判断这些 `.dat` 到底是什么（证据链）

1. **6134 个文件里是 PNG 数据**：`00 00 00 0d 49 48 44 52`（IHDR chunk）+ `49 44 41 54`（IDAT）+ zlib 流（`78 5e`/`78 9c`/`78 da`），且宽高与头部字段逐文件吻合。
2. **60 个 `0x0d` 文件**也是图片：如 13085.dat `33 1d 0d 00 48 00 48 …`（72×72），偏移 52 起是可用 `zlib.decompress` 解开的流（实测解出 5256 字节）。
3. **`classes.dex` 里的引擎包名直接点名了这套体系**：
   ```
   LengineBase/res/Res;          LengineBase/res/ResManager;    LengineBase/res/ResChannel;
   LengineBase/res/HttpResChannel; LengineBase/res/RmsResChannel; LengineBase/res/SocketResChannel;
   LengineBase/res/Png;          LengineBase/res/SpriteInfo;    LengineBase/res/SpriteInfo$SpriteFrame;
   LengineBase/res/MapInfo;      LengineBase/res/ActLayer;      LengineBase/res/AttrLayer;
   LengineBase/res/SurfaceLayer; LengineBase/res/WapLayer;      LengineBase/res/TileLayer;
   LengineBase/res/RuleTileLayer;LengineBase/res/RandomTileLayer;
   （方法名：getSpriteFrame / getSpriteFrameNum / setSpriteFrame / getSpriteInfo …）
   ```
   即 `.dat` = 该引擎的**序列化资源对象**，`assets/data/<id>.dat` 就是"按资源 id 取资源"的资源库；
   `type` 字节对应 `Res` 的子类（图片/精灵/地图/图层…）。
4. 配置里还有资源服务器：`YgbResUrl=http://resource.3gking.net:8080/` + `/game/res/`、`/game/script/`、`/game/dynamics/`
   → 资源是可下发/可热更的，再次印证 id 是资源编号而非协议号。
5. `assets/929.dat ~ 932.dat` 与 `assets/data/929.dat ~ 932.dat` **四个文件逐字节相同**（在 data/ 之外根目录再放一份，属资源覆盖/兼容副本）；`assets/x.dat`（1296 字节）与 `assets/xdt.png` 未在本次范围内定性。

**结论：`.dat` 是「资源包」，不是「消息字段定义」。** 里面没有字段名、字段类型、字段顺序、消息 id→字段的映射表。

## 7. 对「能否用它推出 op 4128 响应字段含义」的明确判断

**不能。** 逐条说明：

1. **文件内容层面**：4128.dat 只有 6 个字节，语义是 `(自身资源id=4128, 类型=0x06, 父资源=4099, 帧序=28)`，
   是「4099 这张 400×200 精灵图里的第 28 格」，与「加点/角色资源」这类**业务消息的字段**没有任何关系；
   type-6 全部 3015 个文件都是这个形状（引用父资源 + 帧号），不可能承载 56 字节响应里的字段布局。
2. **统计层面**：这些文件里不存在任何"字段宣言"结构——没有字符串、没有 (tag,type,value) 三元组、没有子序列，内容全是图像/帧/图层/引用数据。
3. **"op = 文件名" 的推断本身不成立（关键提醒）**：
   `文件名 == 文件头前 2 字节` 对 **9475/9475** 个文件成立，因此拿任意一个"已知 op"（4099/4100/4108/4128/5128/5130）去比对，都一定会"验证成功"。
   这是**同义反复**，不能作为「这些 id 就是协议操作码」的证据。真正需要证明的是"这些数字是消息号"，而目前观察到的语义全是资源语义（父资源+帧号、flags 别名、精灵帧表）。
4. `5128/5129/5130/5131` 这批 type-3 文件同理：其内容是 10~11 字节记录 `28 01 <u16 图片id> …`，
   实测 **2060/2060 个被引用的 id 都是存在的、且类型全是 0x01（图片）**，即"一串图片引用 + 参数"，属于组合/动画类资源，不是加点/捐献的字段定义。
5. 要拿到 op 4128 响应的字段结构，正确路径是**客户端代码 + 报文**，而不是这些资源文件：
   - 反编译 `classes.dex`，看协议读写类（`engineBase/io/Packet`）中 op=4128 的 parse 逻辑；
   - 抓包看 op 4128 请求/响应（响应 op = 请求 op + 28672）的字节流并做字段对齐。
   本次分析已确认：`assets/data/*.dat` 对这条路径**没有帮助**。

## 8. 明确标注的不确定项

1. type 0x01 中 8 字节帧记录的**完整字段打包方式**（字段顺序/是否有变长编码）未完全确定；只确认了记录条数 = N、与 50 步进网格吻合、末尾 4 字节为负载长度。
2. `[0x08]` 字节的含义未确定（绝大多数为 0；5187.dat=5、6783.dat=1、个别=8/12）。
3. `type` 字节 → `engineBase.res.*` 具体子类的**逐值映射未经反编译确认**（0x01≈Png/图片 是确定的；0x04 疑似 MapInfo/地图，0x06 疑似 SpriteFrame 引用，属合理推测，未证实）。
4. type 0x0d 的 chunk 头改写规则（`78 5e` 等非标准 zlib 头）未完全逆向。
5. `assets/x.dat`（1296 字节，疑似加密/散列数据）未定性。
