### 1.1 各层职责

| 层级 | 技术栈 | 部署 | 核心职责 |
|------|--------|------|----------|

## 二、核心设计原则

### 2.1 登录与功能分离

```
登录流程（仅一次）:
  用户添加账号 → 保存到业务层DB
  ↓
  自动化层启动 → WebSocket连接建立
  ↓
  自动化层登录游戏 → 保持会话
  ↓
  等待用户指令

功能执行（按需触发）:
  用户勾选功能 → 保存配置 → WebSocket通知
  ↓
  自动化层读取配置 → 开始执行已勾选功能
  ↓
  用户可随时修改配置 → 即时生效（无需重启）
```

**关键点**：
- 游戏账号登录后只保持在线，**不自动执行任何功能**
- 功能执行完全由用户配置控制
- 配置修改即时生效，无感切换

### 2.2 分层解耦

```
┌────────────────────────────────────────────┐
│              前端层 (UI)                     │
│  - 配置表单                                 │
│  - 状态展示（日志、进度、军情）                │
│  - 用户/账号管理界面                          │
└────────────────┬───────────────────────────┘
                 │ HTTP API
┌────────────────▼───────────────────────────┐
│              业务层 (PHP)                    │
│  - 用户注册/登录/鉴权                        │
│  - 游戏账号CRUD                             │

│  - UUID设备绑定                              │
└────────────────┬───────────────────────────┘
                 │ WebSocket
┌────────────────▼───────────────────────────┐
│              自动化层 (WS Server)            │
│  - 游戏协议引擎（138个操作码）                 │
│  - 游戏账号登录/保活                          │
│  - 功能调度器（读取配置→按需执行）              │
│  - 心跳检测 + 掉线重连                        │
│  - 军情监控 + 推送                            │

```

### 3.2 HTTP API 清单

#### 用户模块

| 接口 | 方法 | 参数 | 返回 | 说明 |
|------|------|------|------|------|
| `/fz/Login/index` | GET | - | HTML | 登录页 |
| `/fz/login/mobile_login` | POST | mobile, pwd | `{status, msg}` | 手机号登录 |

| `/fz/Login/forget` | GET | - | HTML | 忘记密码 |
| `/fz/Login/regwxurl` | GET | - | HTML | 注册页 |

#### 配置模块

| 接口 | 方法 | 参数 | 返回 | 说明 |
|------|------|------|------|------|
| `/fz/Set/set` | POST | 完整配置JSON | `{status, msg}` | **保存所有配置** |
| `/fz/Set/del_account` | POST | a_id | `{status, msg}` | 删除游戏账号 |
| `/fz/Index/index` | GET | agent_id | HTML | **主功能页面**（含配置渲染） |

## 五、自动化层核心逻辑

### 5.1 主循环设计

```
function main_loop():
    while True:
        # 0. 检查掉线
        if 掉线检测:
            重新登录游戏
            continue
        
        # 1. 读取当前配置
        config = get_config_from_db(a_id)
        
        # 2. 按顺序执行已启用的功能
        if config.changgui.zhiliao_soldier_open:
            step_治疗伤兵()
        
        if config.shuahuang_max > 当前刷黄次数:
            for 编队 in config.saohuang:
                if 编队.open:
                    step_刷黄(编队)
        
        if 任意掠夺编队.open:
            for 编队 in config.lueduo:
                if 编队.open:
                    step_掠夺(编队)
        
        if 任意抢城编队.open:
            step_抢城()
        
        if 任意无损编队.open:
            step_无损()
        
        if 任意挖矿编队.open:
            for 编队 in config.mining:
                if 编队.open:
                    step_挖矿(编队)
        
        if 任意镖车编队.open:
            step_镖车()
        
        if 任意副本编队.open:
            for 编队 in config.fuben:
                if 编队.open:
                    step_副本(编队)
        
        if config.changgui.auto_build_open:
            step_自动内政()
        
        # 3. 军情监控（并行）
        check_军情()
        
        # 4. 等待下次心跳
        sleep(45秒)
        
        # 5. 每次循环重读配置（保证即时生效）
```

### 5.2 功能执行原则

1. **每次循环重读配置** — 用户修改配置后，下次循环即时生效
2. **功能间独立** — 每个功能不阻塞其他功能
3. **次数上限控制** — 刷黄/副本等有限次数的功能到达上限后自动跳过
4. **错误重试** — 单次失败不影响全局，但连续失败告警
5. **日志推送** — 每个关键步骤通过 WebSocket 推送到前端

### 5.3 游戏协议对接

自动化层通过**游戏操作码（Opcode）** 与游戏服务器通信。

已知操作码（基于之前逆向成果，共138个）：

## 八、关键设计要点总结

### 8.1 商业架构的关键特性

| # | 特性 | 说明 |
|---|------|------|
| 1 | **登录与功能分离** | 登录后只保活，不自动执行任何功能 |
| 2 | **配置驱动** | 功能的启停完全由配置控制，不改配置就一直按上次的跑 |
| 3 | **即时生效** | 保存配置 → WS通知 → 下次循环读取新配置 → 立即调整执行 |
| 4 | **WebSocket实时通信** | 所有状态推送、进度显示、军情警报都通过WS实时推送 |
| 5 | **心跳保活** | 自动检测掉线并重连，支持断线后重连继续执行 |
| 6 | **多编队支持** | 刷黄/掠夺等支持多组编队，轮流执行 |
| 7 | **配置持久化** | 所有配置存MySQL，关闭页面再打开配置还在 |
| 8 | **UUID设备绑定** | 支持设备免密登录 |

### 8.2 与普通版架构的区别

```
普通版（你的GitHub项目）:
  启动 → 开始执行（功能硬编码） → 改功能需重启

商业版（鸣牛助手）:
  启动 → 保持登录 → 等待配置 → 按需执行 → 随时改配置即时生效
```
